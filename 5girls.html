Access to your 5 girls

概要

企画開発部、2025年夏みんげーチーム開発で開発したゲームです。

主人公はある日5人の女の子と巡り合い、それを皮切りにして激動の日々を過ごしていきます。 ゲーム内で日付が進んでいき、日が経つにつれて5人のヒロインの裏の顔や隠された秘密を知っていきます。

複数エンドを採用しており、ゲーム後半の選択肢によって分岐します。ヒロインエンドを踏んでしまった場合は最終日前にゲームが終わってしまうため、プレイヤーは無事に最終日を踏むことを第一目標としてプレイしていきます。

プレイ画面はゲーム内のデスクトップ画面とヒロインとのデート画面の2つに分かれており、PCでやり取り→現実でデートを繰り返しゲームが進んでいきます。

サークルの公式サイトからコミックマーケットで頒布したものがダウンロードできます。

こちらの作品が収録されているのは2025 Winterになります

工夫した内容

ゲームの時間システムを作る際に、一番気をつけたことは"日付"と"時間"の分離です。

問題提起

    私は日付と時間を統合してしまうと時間の巻き戻しや日付を跨ぐイベントの処理が難しくなってしまうと考え分離しました。

解決法

以下のようにクラスを分離して設計し、管理しました。

  • calendarDayModel: ゲーム内の1日としての単位クラス
  • calendarWeekModel: ゲームの全体の週としてのモデル、これとcalendarDayModelをhas-a関係で結ぶことによってゲーム全体の週を再現する。
  • calendarController: 日付を管理するコントローラー。カレンダーを操作するクラス
  • EventNodeRegistryModel: その日発生するイベントを保持する"スタック"のようなもの。日付が変わるたびに前日のイベントを全て空にして次の日のイベントを入れる。
  • GameTimeModel/Controller: 0時から24時までをカウントするただのタイマーとして実装

EventNodeRegistryModelの一部


    //その日のイベントを空にして、次の日のイベントを入れる関数
    public void InitializeList(int dayNumber)
    {
        if (dayNumber < 0) return;

        EventNodes.Clear();
    
        Debug.Log(dayNumber);
        
        string path = "ScriptableObjects/EventNodes/Day" + dayNumber.ToString();
        Debug.Log("path");
        Debug.Log(path);
        var all = Resources.LoadAll(path);

        foreach (var e in all)
        {
            if (String.IsNullOrEmpty(e.fireTime))
            {
                Debug.LogError($"[EventNodeRegistry] {e.name} の fireTime が空です。");
                continue;
            }

            EventNodes.Add(e);
            //ForDebug
            Debug.Log(e.nodeId);
            Debug.Log(e.fireTime);
        }

    }

結果

実際にこの設計によって以下のメリットを得られました。

  • 日付を跨ぐ処理(例えば翌日の深夜1時に終了するイベント)をその日の25,26時間目として扱うことでバグを回避できた。
  • 新たに日数を増やしたり、間に新しい日を入れたりすることが容易になった。

苦労した点

今回のプロジェクトでは大きく苦労した点が2点あります。

1点目は時間関連のシステムが私に属人化してしまったことです。

時間システムについて、担当したのが私1人かつ、設計が少し複雑なこともあって時間システムに対応できるのが私とPMのみとなってしまいました。

使用についてPDFにまとめたり、理解を広げるよう努力しましたがあまり実を結ばずとても苦労しました。

実際この出来事で、私のコードをあまり読んでもらえず苦労したので、この後からのプロジェクトで他人のコードを積極的に理解しようとしています。

2点目は開発終盤のアクシデントについてです。

開発終盤、シナリオを書いていたメンバーがやむを得ない事情で継続的な参加が難しくなる状況が発生しました。

その結果、シナリオが断片的に残された状態で全体像がわからなくなってしまいました。

そこで私は、開発自体を止めないことを優先しシナリオの内容把握と連結に取り掛かり、断片的なシナリオを読み込みつつ、不明点はオンラインで担当メンバーと連携しながら確認し、実装できる形でチームで共有しました。

このプロジェクト内で、自分の担当した分野が属人化し、対応できる人が自分だけという苦しみは体感していたので、それを解消できるように動きました。

結果として、開発が滞ることなく作品を完成まで持っていくことができました。

特に、担当した範囲が属人化してしまう問題はとても苦労したのでそうならないよう動く必要性を感じました。
